# Decisions

This file has three lists:

- **Decided:** what the brief settled, plus answers given since.
- **Proposed:** choices made while planning. Accept or overturn them by editing this file.
- **Open:** questions that still need an answer. Each has a `type: decision` issue.

When an open question is answered, move it to Decided with the date, update any affected docs and configs in the same PR, and close its issue.

Notes on the 2026-11-23 answers:

- **D13 raises the preflop cost.** The brief's estimates assumed 6-max, and it puts 8 players at 3 to 5 times the preflop cost. See the risk list in [ROADMAP.md](ROADMAP.md#risks).
- **D14 and D15 together** put 7.5bb in the pot before the first action in C and D: 0.5 + 1 + 2 from the blinds and straddle, and 4 from the antes.
- **D16's cap is 6bb in every config.** The answer was "capped at 6bb (x3 straddle)". It was first recorded as 3 times the effective blind, which gave 3bb in A and B, and on 2026-11-24 it was confirmed as 6bb there too. The raked river test spots keep a cap of 3bb of their own, which binds in more of their pots.
- **D16 replaces the brief's "zero rake for validation".** Test spots set their own rake, so the first reference comparisons can still be rake-free.

## Proposed

| ID | Proposal | Why |
| --- | --- | --- |
| P1 | Integer chips, with 1bb = 100 | Exact pot arithmetic and ties, with rounding done in one place |
| P2 | Preflop sizes are multiples of the effective blind (the largest live forced bet) | The straddle configs scale on their own: a 2.5x open is 5bb under a 2bb straddle, and no code special-cases the straddle |
| P3 | The `cfr` crate knows nothing about poker and holds both scalar and vector-form helpers | One regret implementation for toy games, preflop and postflop |
| P4 | MCCFR and vector-form CFR are validated on Leduc in M2 | Removes risk from M3 and M7, where bugs are harder to see |
| P5 | Postflop parallel work reduces in a fixed order | Results are bit-identical for any thread count, so tests can be exact |
| P6 | The preflop solve accumulates the average strategy only at preflop nodes | Only the preflop strategy is exported, so this saves memory (Pluribus does the same) |
| P7 | The showdown assumes equal live stacks, and the config loader rejects a config whose forced bets leave them unequal (revised 2026-11-23) | Per-player antes (D14) keep live stacks equal, so side pots can't occur. A big blind ante would have needed them |
| P8 | Range files are TOML holding standard range strings | They can be typed by hand from a reference and diffed, and the same file serves export |
| P9 | Postflop nodes store only the combos that are in range | Memory |
| P10 | The abstraction's river equity reuses the showdown sweep, once per board | The code is shared, and the pass takes minutes instead of hours |
| P11 | EMD between 1-D histograms is computed as the L1 distance between CDFs | Exact in one dimension, so no optimal-transport solver is needed |
| P12 | The straddler keeps the position name UTG | Formation names stay the same across configs |
| P13 | Packages are prefixed `pk-` | A crate named `core` collides with Rust's built-in `core` |
| P14 | Each milestone has one gate issue holding its acceptance tests | Makes the brief's "tests pass before moving on" rule visible in the tracker |
| P15 | `[postflop]` has two table-level fields that apply to every street. `max_raises` caps the raises per street after the opening bet (0 means none). `allin_threshold`, more than 0 and at most 1, turns into all-in a bet or raise that would commit more than that fraction of the effective stack. Configs A to D set 3 and 0.67 | Issue [#25](https://github.com/Ollienel777/poker-solver/issues/25) names both rules, the schema had no field for either, and reference solvers expose both knobs |
| P16 | The range-file format lives in `pk-game`, in `pk_game::range_file`, not in `pk-core` as first planned | A range file needs both `Range` and `Position`. `Position` is in `pk-game`, which depends on `pk-core`, so only `pk-game` can see both |
| P17 | Postflop exploitability is the average gain from deviating, `((BR_0 − v_0) + (BR_1 − v_1)) / 2`, where `v_i` is player `i`'s expected value when both play the strategy and `BR_i` its value when it best-responds. Values are in chips per hand dealt, with the deal normalised so that the weights of all the pairs of hands that can be held together sum to 1, and the result is reported as a percent of the pot at the root | Payoffs count from the start of the tree, so the two values sum to the pot minus the expected rake. The game is constant-sum only without rake, since a rake grows with the pot up to its cap. `(BR_0 + BR_1) / 2` would be about half the pot at an equilibrium. In a zero-sum game the two definitions agree |
| P18 | One CFR iteration is specified exactly in the `pk_cfr::regret` and `pk_cfr::tabular` module docs. Iterations count from 1. Players update in turn within an iteration, player 0 first. The discount of iteration `t` is applied after that iteration's regret and strategy are added. Values are computed in `f64` and rounded to `f32` only when stored | CFR+ and DCFR are defined with alternating updates, and one written specification is what lets the vector form and the postflop solver reproduce the scalar solver |
| P19 | MCCFR accumulates the average strategy in a separate pass that samples the player's own actions, and applies discounts lazily from a last-update stamp per information set | Adding the strategy at sampled opponent nodes also weights by the other opponents' reach once there are three or more players. Lazy discounting is exact and never walks every information set |
| P20 | The vector form is held to the scalar solver one iteration at a time from the same stored state, under every schedule. Side-by-side runs are required to match only under vanilla CFR and DCFR on Leduc | CFR+, linear CFR and DCFR can all grow a one-ulp `f32` difference past 1e-6 within tens of iterations, so two correct solvers that sum in different orders can part ways. On Leduc that happens under CFR+ and linear CFR after about 10 and 130 iterations. Measured in [#21](https://github.com/Ollienel777/poker-solver/issues/21) |
| P21 | Leduc treats its six cards as distinct, which gives 936 information sets | The vector form keeps one entry per private card, so the scalar game is a one-to-one target and exercises card removal the way hold'em will |
| P22 | A node's strategy over a range has two read-outs. `range_view_frequencies` weighs each hand by the player's own range weight and reach, and is what comparisons and range views use. `action_frequencies` also weighs by how much of the opponent's range each hand leaves possible, and is the probability of the action at the node | The two differ by up to 8.7 percentage points on the river test spots. Other solvers' range views use the first, and a comparison must use one weighting on both sides. Found by the review of [#85](https://github.com/Ollienel777/poker-solver/pull/85) |
| P23 | A flop or turn spot is solved on a public tree that expands the betting tree: each chance node has one child per card that can fall, the root of a copy of the betting below it, and every node knows its betting node and its board | `VectorCfr` stores one row per node and walks a tree, so it solves the expansion with no change to `pk_cfr`, and the size the expansion costs is what the memory estimator ([#38](https://github.com/Ollienel777/poker-solver/issues/38)) will measure. Keeping one betting tree with per-card data beside it would need a solver walk that knows about cards. Merging suit-isomorphic branches is [#39](https://github.com/Ollienel777/poker-solver/issues/39), after a benchmark |
| P24 | A chance node's outcomes are every card off its board, each with probability `1/(48 − b)` on a board of `b` cards, and each rules out the hands that hold its card | Once both players hold their hands, the next card is equally likely to be any of the `48 − b` cards neither holds, so for every pair of hands that can be held together the outcomes that rule out neither sum to 1, as `PublicGame` requires, with no special case. Leaving out a card that rules out a whole range would save a subtree in rare spots, and would need care to keep the distribution |
| P25 | Each player's hand list is the spot's, on its own board, for the whole game. A hand that holds a dealt card stays in every per-hand vector below it, with reach zero, and plays uniformly there | `VectorCfr` has one hand count per player for the whole game, so per-street hand vectors, which issue [#36](https://github.com/Ollienel777/poker-solver/issues/36) mentions, would change `pk_cfr`'s API. The cost is the ruled-out entries: a card is in 48 of a flop's 1,176 combos, so about 4% of each vector on the turn and 8% on the river. To revisit once the memory estimator measures it |
| P26 | Each terminal is evaluated on the board it is reached on, with a `BoardHands` built once for every board the public tree reaches. A river board's hands are ranked once and shared by the two orders its last two cards can fall in. The opponent's reach is gathered into the board's hand order and the values written back by an index into the spot's lists | One implementation of the fold and showdown sweeps serves every street, the river's unchanged, and the evaluator stays out of the loop. Folds could be evaluated on the spot's board, since the solver passes zero reach for ruled-out hands, but the gather gives the right values whatever reach it is given. A second, root-indexed sweep that skips blocked hands would duplicate the sweep |
| P27 | The game is one type, `PostflopGame`, and `RiverGame` is an alias of it. `PostflopGame::new`, which the river code calls as `RiverGame::new`, still takes river spots only and fails with `SolveError::NotRiver`; `PostflopGame::from_spot` takes any street. The dump, its import and the comparison stayed river-only, refusing a flop or turn solution, until P30 | The river tests and the river-only code work unedited, a river solve is bit-identical to M3's, and there is one implementation of the payoffs and the evaluation. A second game type beside `RiverGame` would have two that could drift, and renaming it would edit every river test. A river-only constructor keeps code that needs a river game from being handed a flop game |
| P28 | The public tree has a node limit, `SolveOptions::max_nodes`, a million by default like the betting tree's. Its size is counted from the betting tree before anything is allocated, and a tree over the limit is refused with `SolveError::PublicTreeTooLarge` | A flop line that reaches the river is copied 49 × 48 times, and an unbounded build can take the machine down. The count is exact and cheap. The limit bounds nodes, not storage, which grows with the hands as well; the memory estimator ([#38](https://github.com/Ollienel777/poker-solver/issues/38)) bounds storage |
| P29 | A public node is named by its path of action tokens and cards, such as `x b50 c 7s x`, through `PostflopGame::find` and `PostflopGame::node_path`. A solution's node indices are the public tree's. Below a card, a hand that holds it has reach 0 and is not in the range, and `reach_probability` includes the chance of each card dealt on the way | The comparison, the example and `inspect` need to name nodes below a card, and the CLI's node paths already write cards so. With the cards' chance in it, `reach_probability` is the probability of the line and sums over a chance node's children to the chance node's; conditional on the cards, it would not |
| P30 | The dump, its import and the comparison handle every street, which amends P27: a river spot's dump is version 1, as before and byte for byte, and a flop or turn spot's is version 2. The version follows from the board, and `SolutionDump::complete` is always true in version 1. `RiverGame::new` keeps refusing a flop or turn spot for code that needs a river game | One reader, mapper and comparison for every street, so that the river's checks are the turn's and the flop's. Deriving the version from the board leaves no way to write a river spot as version 2, or the reverse, from code |
| P31 | A path is one list of `DumpAction`s, which gains a variant `Deal(Card)`; a node's `actions` never hold one | The specification makes a path one list of everything public, actions and deals. A separate step type would have changed the type of every path, and every river test and message that names one |
| P32 | Version 2's reader walks each path through the betting, from the dump's own stack, board and hands: where each deal falls, each action's legality and amount (a street total no larger than the player had left when the street began), no step after a fold, the river's close or an all-in called, a path that ends at a decision, a node's actions legal where it stands, and each card dealt one that can fall. A card can fall when some pair of hands, one of each player's in `spot.hands`, sharing no card and missing the board as it stands (the cards dealt on the path included), misses it. Version 1's reader is unchanged and makes no such walk | These are rules a file can break that need nothing but the file, so they are refused there with the field, before the spot or the tree is looked at: amounts written as totals over all streets show at the first all-in that passes what is left. The specification's "sharing no card, both miss" does not say whether the pair must miss the cards dealt earlier; requiring it is what "can fall" means, since a pair that holds the turn card is not there at the river, and the reference's wrapper does the same (measured on a flop spot where the two readings differ). Leaving version 1 alone keeps the river exactly as it was |
| P33 | The tree stage expects exactly our decision nodes on the streets the dump holds, after every card that can fall, and reports the cards after which the dump has no node once per deal (`Mismatch::MissingCards`). Our subtree after a card that cannot fall is not expected, and its strategy is filled in as uniform | Completeness is checked against our tree, like the rest of the tree, so that every difference is listed at the shallowest place: a missing card, or a street listed for some lines only, is one report at the deal rather than one per node below it. No hand dealt reaches a subtree after a card that cannot fall, so its strategy changes no value, best response or EV |
| P34 | A partial solution, of the first one or two streets, holds the strategy on those streets only, and is filled in as uniform below them. Its exploitability is not measured (`MappedSolution::exploitability` is `None`); the verdict holds its solver's own figure to the limit, compares the values it reports, and lists both in `Comparison::unchecked`, and the text says plainly that they could not be checked here. Its EVs are measured at a node only when it holds the node's whole subtree | Measuring a strategy needs all of it. Comparing what both hold keeps the flop, where the strategy matters most and a complete dump runs to a gigabyte, comparable at all; marking the reported figures as reported keeps them from being mistaken for measured ones |
| P35 | A node is checked when either strategy reaches it more than `min_reach` given the cards dealt on its path: its reach over the probability that those cards fall. On the first street that is the reach, so a river spot is checked as in M3 | Below a deal the raw reach is at most 1/45 per card, so a 1% threshold would check nearly nothing, and a strategy right on the flop and wrong after a turn card would pass. Given its cards, each runout's subtree is a game of its own, and a line taken a third of the time on it is checked whatever the card. Summing over the cards would check something, but would dilute an error after one card 45 times; conditioning on reaching the chance node too would check lines the strategy almost never takes |
| P36 | The frequency limit below a deal is a separate setting, `Tolerances::frequency_below_deals`, one value below one deal and one below two; `Tolerances::frequency` keeps the M3 gate's 2 points for the first street, and a river spot never reads the new field. Its default is 10 points below one deal and 25 below two. It is a proposal: the M4 gate's owner sets the flop and turn tolerance | Measured by `honest_solvers_table_by_street` (ARCHITECTURE.md, Cross-solver comparison): at 0.03% of the pot, two honest solves of the spots with about a hundred combos a side or more differ by under 1 point on the first street, by up to 7.7 points below one deal and up to 18 below two, since the exploitability is an average over the runouts and each runout's subtree is less converged than the whole; the default adds about a third. The differences shrink with convergence on such spots, so a tighter target is the other way to a tighter limit. On narrower ranges they reach 15 to 34 points even at 0.01%, because a hand that is a large share of a range can mix in any proportion where it is indifferent: there no per-node limit tells sound from wrong, and the exploitability of a complete dump and the reported EVs hold the later streets |
| P37 | The text of a flop or turn comparison lists the first street node by node, as the river's does, sums up each later street, and lists the checked nodes below a deal that differ most; a river comparison's text is unchanged | A flop comparison holds tens of thousands of nodes, which no one reads one by one |
| P38 | The turn and flop fixtures' trees can be reproduced by a solver that sizes in fractions. Every bet and raise, on every street and line, is a whole number of chips before rounding and at least 1bb, and none reaches the stack, so no size is lifted, turned into all-in or merged with another, and every all-in is what the player had left when the street began. `tests/street_spots.rs` walks every tree to hold this | The reference rounds a fractional chip and lifts a small bet differently from this solver, and `postflop-ref` refuses a tree where either shows; what a solver does with a size past the stack is a rule of its own. With every pot of a single-raised spot 550 chips times a whole number, half-pot and pot-sized bets and raises to 3× stay whole on every line |
| P39 | The raked turn and flop fixtures take 5% with a cap set for each spot, so that it binds in some of the spot's pots and not in others, and never exactly at the cap: 1bb on the single-raised flops, 2bb on `called_flop_raise_allin`, and the configs' 6bb on `three_bet_low_spr` | The configs' 6bb (D16) binds in no pot of a reduced single-raised flop, whose largest pot, 88bb, pays 4.4bb, so the cap would go untested there. The river spots' 3bb was chosen the same way |
| P40 | The postflop benchmarks run on two fixed spots in `crates/postflop/benches/data`, both with about 300 hands a side: `turn_srp`, with two bet sizes, a raise and all-in on the turn and the river (16,317 public nodes), and `flop_srp`, a 100bb single-raised pot with one half-pot bet per street and no raise (191,844 public nodes, about 2 s an iteration). Each benchmark checks the hand counts and the node count before it times anything. An iteration is timed on a copy of the solver after 5 iterations | Realistic hand counts, because the profile changes with them: on the same flop tree with 16 hands a side, two thirds of an iteration is spent per node whatever the hands, and with 300 the terminal sweeps lead. The flop tree is the smallest with every street, so an iteration stays near 2 s, and it is the first of the flop solves whose cost was asked for. Copying the solver makes every timed iteration the same one from the same state. The checks stop a change to the tree builder or the ranges from changing a benchmark unnoticed |
| P41 | The memory estimate follows the solver's code allocation by allocation, overheads included: two average-strategy profiles during a measurement, and at the end when the solve stops after an iteration it did not measure; the pure strategy a best response builds; the copy of the game in the solution; the solver's row headers and its flag per hand and node; and, in a build with debug assertions, the invariant check. It estimates each phase of the solve (building, iterating, measuring, finishing) and takes the largest. The two layouts private to `pk_cfr` are mirrored by structs with the same fields | An estimate of a tidier solver would be about half too low on the flop benchmark spot, where the profiles and the best response are 0.55 GB of the 1.05 GB peak. The estimate's job is to stop solves that do not fit, so it must be of the code as it is, and a test against a counting allocator keeps it in step with the code. A method of `pk_cfr::VectorCfr` reporting its own storage would replace the mirrors |
| P42 | The solve compares `MemoryEstimate::total` with `SolveOptions::max_memory`, 10 GB by default, read as 10^10 bytes. The total is the heap at the peak, a margin of 1/256 and 4 KiB for allocations too small to follow, an allowance for the allocator of 32 bytes per live allocation and 1/16 of the bytes, and 16 MiB for the process. The estimate's test requires the heap estimate to be at or above the peak a counting allocator measures, and within 5% of it | The limit is about what the machine holds, so it is compared with a figure that includes what the allocator and the process add: on the benchmark spots the total came 6% (flop) and 14% (turn) above the measured peak resident memory. Decimal gigabytes are the smaller reading of D17's 10 GB. Never below, since a low estimate lets a solve run out of memory; within 5%, since the heap estimate came within 0.4% of the measured peak on the larger test spots and within 3.6% on the smallest, a river spot of half a megabyte, and a larger gap would mean an item counted that the solve does not hold |
| P43 | The peak resident memory of the process comes from `VmHWM` in `/proc/self/status` on Linux and from `PeakWorkingSetSize` of `GetProcessMemoryInfo`, through `windows-sys`, on Windows, and is unknown elsewhere. `windows-sys` is a dependency of `pk-postflop` on Windows only | It is the one operating-system call the log needs. `windows-sys` is Microsoft's own binding crate, MIT or Apache-2.0, and was already in the lock file through the development dependencies; Linux needs no crate. `memory-stats` and `sysinfo` report the current resident memory, not its peak |
| P44 | The resource log's record, `SolveRecord`, and `append_record` are in the library, and the caller names the file. A record is one line of JSON with the spot, its tree sizes and hands, the whole itemized estimate, the peak resident memory, the wall time, the iterations, the stopping rule, the exploitability, the target and caps, whether debug assertions were on, and the operating system. The example `solve_spot` appends one per solve to `runs/log.jsonl` unless `--log` or `--no-log` says otherwise, and `--estimate` prints the estimate without solving | The library never writes a file on its own, and the CLI will reuse the record. With the whole estimate in each line, the log shows which item was off when the peak and the estimate part. A build with debug assertions takes more memory and time, so each record says which build made it |
| P45 | The walks of `pk_cfr::vector` and `pk_cfr::vector_best_response` keep their working memory instead of allocating it at each node. A node with children takes a frame of buffers (its strategy, the reaches it passes down, the possible hands after a card, its children's values) from a stack of frames and gives it back when it returns, so the node at each depth always takes the frame the last node there used. A buffer is refilled in place and grows only when asked for more than it holds, and then to exactly that (`reserve_exact`). `VectorCfr` keeps its walk's working memory from the first iteration on, for both players; each best-response and expected-value walk makes its own and drops it, and the check of the tree's shape before a walk holds its possible hands the same way. What remains allocated per node is the best response's own strategy, which it returns | After the first iteration an iteration allocates nothing (147,000 allocations on `turn_srp` and 1.79 million on `flop_srp` before), and every value is computed from the same values in the same order, so every result is bit for bit the same. A stack of frames is a value that a walk of any subtree can own, empty to start with, so the parallel walks of #40 can each have one; a pool owned by the solver and borrowed through the whole walk would have to be torn out for them. Exact growth makes the buffers' sizes a function of the tree, which the memory estimate follows. Rejected: one arena carved into slices down the line, which needs a sizing pass repeating what every node needs; a free list of vectors of any size, whose sizes drift and settle at no known iteration |
| P46 | `PublicGame` gains two provided methods. `hands_ruled_out(node, outcome, player)` lists the hands an outcome rules out, by default by testing every hand with `rules_out`; the walks and the shape check use it. `terminal_values_with(…, scratch)` is `terminal_values` with a `Vec<f64>` the walk keeps from terminal to terminal, and by default ignores it. `terminal_values` keeps its signature, and `PostflopGame`'s calls `terminal_values_with` with an empty vector | Leduc, the test arenas and the wrapper games of the tests compile and behave as before without a line changed, and a game that does not provide the new methods is only slower. Rejected: an associated scratch type, which every implementation would have to name, associated type defaults not being stable; a scratch parameter on `terminal_values`, which changes every implementation and every test that calls it for the needs of one game; interior mutability in the game, since a `RefCell` makes it `!Sync`, which #40 needs it to be, and a thread-local buffer hides memory from the estimate and holds it for the thread's life; evaluating a later board on the spot's hand lists without the gather, which changes the order of the sweeps' sums |
| P47 | `PostflopGame` holds, for each player, the spot's hands that hold each card, in hand order, in one vector with an offset per card: 8 bytes per hand. `hands_ruled_out` returns the list for the card the outcome deals. On a later board, the gather of the opponent's reach into the board's order and the values in that order are held in the walk's scratch | An outcome rules out only the hands that hold its card, about one in 25, so a walk sets those instead of testing every hand: the test, once per hand and card for both players at every chance node, was 7.6% of a flop iteration and 12% of a flop measurement.
